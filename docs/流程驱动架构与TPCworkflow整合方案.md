# 流程驱动架构与 TPCworkflow 整合方案

> 版本：v1.0 · 2026-10-19
> 输入：产品方向决议（系统从"数据记录工具"转为"流程驱动平台"，OA 在本平台集成开发）、TPCworkflow 仓库代码分析（https://github.com/dqf514/TPCworkflow.git）、bizSys 现状（`技术设计文档.md` §10、approval 模块实现）
> 结论先行：**以 bizSys 为唯一平台，TPCworkflow 不独立部署，其引擎语义与前端资产迁入合并到 bizSys**；bizSys 全业务按"提交即发起流程"改造；OA 流程走表单引擎配置化，不写代码。

---

## 1. 理念转变：从"保存单据"到"发起流程"

### 1.1 现状问题

bizSys 当前的业务动作本质是**先存记录、后走审批**的弱耦合：合同新建是保存一条 `draft` 记录，审批是可附加的动作；任务新建同理。这导致：

- 单据可以绕过流程直接存在（数据记录工具的典型特征）；
- 业务状态与审批状态两张皮，靠人工对齐；
- 流程引擎只是"审批中心"一个角落，不是系统的主动脉。

### 1.2 目标模型：业务对象的生命周期由流程实例驱动

```
用户动作            系统行为                                业务对象状态
────────────  ──────────────────────────────────────  ──────────────
新建合同草稿   仅暂存表单数据（不生成正式编号）             draft（不可见下游）
提交合同      = flow.start('contract', id, 变量)         pending（流程流转中）
审批通过      流程事件 approved → 业务状态机推进           approved → 生效
审批驳回      流程事件 rejected → 退回修改                 rejected → 修改后重提
```

- **提交 = 发起流程实例**，`business_type + business_id` 双向绑定（TPCworkflow 的 `WorkflowInstance.business_type/business_id` 正是这个设计，直接沿用）。
- **草稿只是流程发起前的暂存**，不进入任何下游统计与关联；正式编号（HT/RW/K/DZ 号）在提交或生效时由编号规则模块发放。
- **业务状态机只响应流程事件**，不允许界面直接改状态；bizSys 已有的进程内领域事件总线（`common/events.py`）是天然载体。
- 全业务按此改造：合同、任务、报告、开票申请、结算单，以及后续 OA 单据（请假/报销/出差/用章/采购）。

### 1.3 无纸化与移动化

- **企业全部工作在系统上流转**：审批意见、电子签名（手写签）、报告签章、附件归档均线上完成，纸质件只作为扫描附件存在。
- **现场录入**：任务执行中，用户用手机/平板/电脑随时录入数据、采集信息、更新任务与报告。落点：
  - bizSys 前端已是响应式桌面级体系（技术设计文档 §7），PAD/手机访问无需独立 App；
  - 重点补齐现场场景组件：扫码（相机调起）、拍照上传、手写签名、语音转文字（二期 AI）；
  - 企业微信 H5 应用入口（已有企微集成基座），扫码/免登直达待办与现场录入页；
  - PWA 化（添加到主屏、弱网草稿本地暂存）列为二期增强。

## 2. TPCworkflow 代码评估（实测结论）

通读仓库后端模型与引擎服务后的能力清单：

| 维度 | TPCworkflow 现状 | 评价 |
|---|---|---|
| 技术栈 | Flask + Flask-SQLAlchemy + Alembic，默认 SQLite；Vue3 + TS + Tailwind；另有 WPF 桌面客户端 | 与 bizSys 同属 Python/Vue3 生态，模型与服务层移植成本低 |
| 流程引擎 | 自研轻量引擎（`workflow_engine.py`）：**条件分支、或签/会签/依次审批、加签、转交、抄送**、选项校验 | 语义完整覆盖 OA 与业务审批，比 bizSys 现行引擎强一档 |
| 流程设计器 | **LogicFlow 2.2 可视化设计器**，模板 key+version 版本化、草稿/发布 | 正是 bizSys"流程配置"页缺的可视化能力 |
| 表单引擎 | `FormDefinition`（schema_json）与流程绑定，管理端可视化建表单 | **OA 流程零代码配置的关键资产** |
| 组织模型 | 公司（多组织）/部门（树形）/用户多任职+主部门/**业务板块** | 比 bizSys 现行部门模型丰富，多任职与业务板块值得吸收 |
| 审批体验 | 手写签名、邮件内快速审批（一次性 token 链接）、发起人进度未读角标、审批时间线（只追加审计） | 全部值得迁入 |
| 周边资产 | 打印模板、选项集（option_sets）、节假日/请假日历、财务凭证导出、收据 OCR（LLM）、运行时 i18n 词典、多方式登录（密码/邮箱验证码/短信/Office365 SSO） | OA 与财务场景的现成积木 |
| 不足 | 非 BPMN 标准（与 bizSys 一样是自研轻量引擎，能力靠代码扩展）；表单与流程 1:1 绑定不利复用；SQLite 默认库需切换 MySQL；WPF 客户端与本项目无关 | 整合时按需裁剪 |

### 与 bizSys 现行审批引擎的差距对照

| 能力 | bizSys 现状（5 表：定义/节点/实例/待办/记录） | TPCworkflow | 整合方向 |
|---|---|---|---|
| 节点流转 | 顺序多级 | 顺序 + **条件分支** | 吸收 |
| 审批方式 | 或签、加签、转办、驳回 | 或签/**会签/依次**、加签、转交、**抄送** | 吸收会签/依次/抄送 |
| 流程定义 | 管理页配置（非图形化） | LogicFlow 可视化 + 版本化 | **移植设计器**，bizSys 流程配置页升级 |
| 表单 | 无（业务表单硬编码） | 表单引擎 | 吸收，用于 OA 域 |
| 签名 | 无 | 手写签名 | 吸收组件 |
| 组织 | 公司单租户 + 部门树 | 多公司 + 多任职 + 业务板块 | 按需吸收（多任职/业务板块优先） |
| 业务绑定 | 合同/报告/开票三类已生产使用 | business_type/id 通用绑定 | bizSys 绑定语义保留，引擎能力对齐 TPC |

## 3. 整合架构决策

### 3.1 决策：合并，而非并行

**bizSys 为唯一运行平台，TPCworkflow 的能力迁入；不采用"双系统并行 + SSO 互通"模式。**

理由：
1. 用户目标明确——"OA 系统也将在这个平台进行集成开发"，平台就是 bizSys；
2. 双系统并行必然带来组织双写、待办割裂、权限两套，违背"企业工作在一个系统流转"的目标；
3. 两边同为 Python + SQLAlchemy + Vue3，移植是"同生态搬家"，不是跨语言重写；
4. bizSys 已有 TPC 没有的关键基座：企业微信集成、三点式权限码、编号规则、字典、审计、菜单管理、业务模块（合同/任务/财务）。

### 3.2 目标架构

```
┌──────────────────────── bizSys ────────────────────────┐
│  flow 流程中心（approval 模块升级）                      │
│  ├─ 设计器：LogicFlow（移植自 TPC 前端）                 │
│  ├─ 引擎：定义/版本 · 实例 · 任务 · 时间线 · 抄送        │
│  │        顺序/条件分支/或签/会签/依次/加签/转交          │
│  ├─ 表单引擎：FormDefinition（OA 单据零代码）            │
│  └─ 体验：手写签名 · 邮件快速审批 · 进度角标              │
│                                                        │
│  业务模块（contract/task/report/finance/oa…）            │
│  └─ 统一接入：submit() → flow.start(biz_type, id, vars) │
│     状态推进 ← 领域事件（flow.approved / rejected）      │
│                                                        │
│  admin：组织（部门/多任职/业务板块）· 权限 · 编号 · 字典  │
│  integration：企业微信（通知/SSO/H5 入口）· 邮件网关      │
└────────────────────────────────────────────────────────┘
```

- **变量驱动分支**：流程变量由业务侧提交时注入（金额、合同类型、业务板块、部门），条件分支节点按变量路由——例如"金额 > 10 万自动加签分管副总"。
- **编号时机**：草稿无编号；提交流程时发"申请号"，流程通过时发正式业务编号（合同 HT 号等），编号规则模块统一受理。
- **OA 域**：请假/报销/出差/用章等**不写代码**，管理员用表单引擎建单 + 设计器画流程即可上线；只有需要联动业务数据（如报销冲抵借款）时才写业务钩子。

### 3.3 迁移策略：直接替换（2026-10-19 修订）

系统尚在开发阶段，**无存量数据包袱，不做新旧并行**，直接替换：

1. **引擎扩容**：bizSys approval 模型增加 TPC 语义字段（`process_graph`、`variables`、`current_node_ids`、抄送表、时间线表、视图水位表），服务层移植 `workflow_engine.py` 语义（Flask-SQLAlchemy → SQLAlchemy 2.x，逐服务翻译 + 单测对齐行为）。
2. **直接切换**：旧 5 表引擎随新引擎上线直接废弃（表结构并入新模型， alembic 迁移重建即可）；合同/报告/开票三处业务绑定同步改为新引擎调用。
3. **设计器与表单引擎上线**：LogicFlow 设计器替换现有"流程配置"页，无旧配置迁移负担。

## 4. 全业务流程化改造清单（bizSys 各模块）

| 模块 | 当前 | 改造后 |
|---|---|---|
| 合同 | 保存 draft + 可提交审批 | 提交即发起"合同审批流程"；变量：金额/类型/客户等级；通过后生效发 HT 号 |
| 任务 | 直接创建 | 提交即发起"任务立项流程"（可按任务类型配置免审直通节点）；通过后发 RW 号并排程 |
| 报告 | 审批→PDF→签章（部分后移） | 报告流程：起草→校核→批准→自动转 PDF→电子签章→归档，全流程线上 |
| 开票/结算 | 已有审批 | 接入统一流程中心，变量驱动（金额区间走不同层级） |
| OA（新增） | 无 | 表单引擎 + 设计器配置：请假/报销/出差/用章/采购/用章；假期日历/考勤规则复用 TPC 资产 |
| 工作台 | 数据卡片 | 以"我的待办/我发起的/抄送我的"为门户核心（流程驱动系统的门户天然是流程视图） |

## 5. 实施计划

| 阶段 | 内容 | 产出 |
|---|---|---|
| F1 引擎合并 | approval 模型扩容 + TPC 引擎语义移植（条件分支/会签/依次/抄送）+ 单测行为对齐 | 新引擎承载新实例，旧实例并行跑完 |
| F2 设计器与流程中心 | LogicFlow 设计器移植（替换流程配置页）；审批中心升级为流程中心（发起目录/待办/已办/抄送/我发起的+进度时间线+未读角标）；手写签名组件 | 业务人员可视化配流程 |
| F3 业务全量流程化 | §4 清单逐模块改造"提交即流程"；编号时机调整；企微待办推送打通 | 合同/任务/报告/财务全链路线上流转 |
| F4 OA 上线 | 表单引擎 + 首批 OA 流程（请假/报销/用章）；假期日历；邮件快速审批 | OA 零代码配置能力交付 |
| F5 增强 | 收据 OCR（报销场景）、财务凭证导出、PWA 现场录入、多任职/业务板块按需启用 | 视业务优先级排期 |

与《风洞数字化技术实现方案》§9 的关系：**F1~F4 并入 P0 基座完善清单**（流程驱动是基座的核心属性）；F5 与风洞 P1~P4 并行按资源排期。

## 6. 风险与注意点

| 风险 | 对策 |
|---|---|
| 两个自研引擎语义对齐有细节坑（加签与或签交互、驳回后重入规则） | 以 TPC 引擎行为为准写行为对照测试集，移植时逐条过 |
| 存量审批实例迁移 | 开发阶段无存量数据，直接替换旧引擎，无此风险（2026-10-19 修订） |
| 表单引擎自由度引发管理混乱 | OA 表单发布走管理审批；业务模块表单不开放自定义 |
| TPC 的非 BPMN 自研引擎天花板 | 与 bizSys 现行选型一致（技术设计文档 §2.1 已决策自研）；未来真需要 BPMN 再评估 Flowable，引擎接口层预留 |
| 多组织/多任职增加复杂度 | 单公司场景先不启用多公司，仅吸收多任职与业务板块维度 |
