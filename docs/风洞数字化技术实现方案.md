## 1. 对 V1 方案的评估：吸收什么、摒弃什么

V1 方案约三分之二篇幅是投标通用内容（SOA 布道、Spring Cloud 组件罗列、项目管理/测试流程套话），真正有价值的是 **业务域划分、设备与安全管理的细粒度需求、19 项外部系统接口清单、性能与安全指标**。

### 1.1 值得吸收的部分

| V1 方案内容 | 评价 |
|---|---|
| 八大业务域划分（客户门户/试验实施/数值风洞/设备/结算/安全/数字孪生/接口） | 业务边界清晰，直接作为模块蓝图 |
| 设备管理细需求（能耗 7×24 采集、NFC 点检、二维码出入库、故障库、工位忙闲） | 一线实操需求，照单吸收 |
| 虚拟结算数据模型（能耗+工时+耗材按任务绑定，自动触发结算） | 与 bizSys 财务链路天然契合，重点吸收 |
| 外来试验人员管理（登记→审核→门禁授权→订单结束自动取消） | 闭环设计好，吸收 |
| 外部系统接口清单（19 项：WTCS/TMS/EAM/TDC/DMDS/数字安保等） | 直接作为集成清单蓝本 |
| 性能与安全指标（并发 300、响应 1s/3s、等保三级、3G 断点续传） | 作为验收口径吸收 |

### 1.2 过时或不采用的部分

| V1 方案选型 | 问题 | 本方案替代 |
|---|---|---|
| SOA + ESB 企业服务总线 | 重型架构，中小规模团队维护不起 | 模块化单体 + 进程内领域事件 + REST/Webhook（bizSys 现有架构已支持未来拆分） |
| Spring Cloud 全家桶 / JDK 1.8 / Tomcat | 版本老旧，组件堆砌（Eureka/Hystrix/Zuul 已停止演进） | 现有 FastAPI 栈；`integration` 模块承担适配器角色 |
| MySQL 5.7 / MongoDB 4.0 | 版本过老；MongoDB 在本场景无明确收益 | MySQL 8 + TDengine（时序）+ MinIO（文件） |
| XML / Web Service 接口 | 上世纪风格，维护成本高 | JSON REST + OpenAPI 3 + Hmac 验签（现有 `openapi` 规范） |
| activiti 7 流程引擎 | 重型 BPMN，超需求 | bizSys 流程引擎：合并 TPCworkflow 语义后具备可视化设计器 + 条件分支/会签/抄送（见 `docs/流程驱动架构与TPCworkflow整合方案.md`） |
| 低代码平台 / 表单自定义平台 | 绑定供应商、二开黑洞 | bizSys 字典/编号规则/流程配置/菜单管理已覆盖"可配置"诉求，表单按代码实现 |
| 网上商城 / 购物车 | 试验服务非标准商品，电商交互过重 | 简化为"服务目录 + 下单向导"（客户门户内） |
| Kafka / RocketMQ 消息队列 | 一期业务量用不上 | 进程内事件总线 + Redis；量级上来再引入 |
| IE7 兼容、短信平台为主通知 | 过时 | 现代浏览器；通知以企业微信为主通道（已有集成），短信兜底 |
| 2023–2024 实施里程碑 | 时间已过期 | 按本文 §9 重新排期 |

## 2. 目标总体架构

```
┌───────────────────────────── 接入层 ─────────────────────────────┐
│  Web 端(bizSys 现有)  │  PAD/PDA H5(扫码点检/工时)  │  客户门户   │
│  数字大屏/VIP 室 TV   │  企业微信(通知/待办/移动审批)              │
├───────────────────────────── 应用层（bizSys 单体，模块扩展）──────┤
│  现有：crm / contract / task / report / finance / approval        │
│       / admin / settings / integration / workbench                │
│  新增：portal(客户门户) device(设备) safety(安全) sim(数值风洞)    │
│       lab(试验实施扩展) twin(数字孪生前端) openapi(开放接口)        │
├───────────────────────────── 集成层 ─────────────────────────────┤
│  IoT 采集服务(Modbus/OPC UA/MQTT/DTU → TDengine)                  │
│  外部系统适配器(WTCS·TMS·EAM·TDC·DMDS·数字安保·财务·视频监控)     │
├───────────────────────────── 数据层 ─────────────────────────────┤
│  MySQL 8(业务库)  │  TDengine(时序：能耗/设备参数)                │
│  Redis(缓存/锁/事件)  │  MinIO(原始数据/报告/数模，分片断点续传)  │
└──────────────────────────────────────────────────────────────────┘
```

**架构原则**：
1. **不拆微服务**。bizSys 模块化单体 + 领域事件的架构（技术设计文档 §3）已预留拆分路径，风洞业务按新模块接入即可，避免 V1 方案的 ESB/微服务复杂度。
2. **时序数据与业务数据分库**。设备参数/能耗是典型高频时序数据（7×24、多变量、按秒/分钟采样），放 MySQL 会拖垮业务库——引入 TDengine（国产、SQL 接口、风洞场景对口；备选 TimescaleDB）。业务数据（台账、点检单、结算）仍在 MySQL。
3. **大文件走对象存储**。原始试验数据、数模、后处理报告（V1 要求 3G+ 断点续传）存 MinIO，前端分片上传（tus 协议或自研分片），业务库只存元数据。
4. **一切对外集成收敛到 `integration`/`openapi` 模块**：AppId/Hmac 验签、幂等、推送记录与重放——该设计在技术设计文档 §8.7/§11 已冻结，19 项外部系统全部按此模式接入。

## 3. 业务模块整合设计（核心）

### 3.1 V1 八大域 → bizSys 模块映射总表

| V1 业务域 | bizSys 落点 | 改造方式 |
|---|---|---|
| 2.1 外部客户管理 | 新增 `portal` 模块 + `crm` 扩展 | 客户门户独立路由组；客户账号/信誉度挂到客户档案 |
| 2.2 试验实施管理 | `task` 模块扩展 + 新增 `lab` 子域 | 任务类型扩展"风洞试验"；排程/样车/整备/工时为新子模块 |
| 2.3 数值风洞 | 新增 `sim` 模块 | 仿真任务/模型模板/后处理，全部经集成层调仿真平台 |
| 2.4 设备管理 | 新增 `device` 模块 | 台账/预警/能耗/点检/物料/工位/故障库 |
| 2.5 虚拟结算 | `finance` 模块扩展 | 结算单增加"用能/工时/耗材"明细来源，数据来自 device/lab |
| 2.6 风洞安全管理 | 新增 `safety` 模块 | 巡检/消防点检/监控告警展示 |
| 2.7 数字孪生 | 新增 `twin` 前端模块 | Three.js 三维 + WebSocket 实时数据，大屏/TV 端 |
| 2.8 接口管理 | `admin` 集成域扩展 | 连接配置/凭证/连通性测试/推送重放（设计已有，补页面） |

### 3.2 客户门户（portal）

- **账号体系**：客户单位账号公开注册 → 内部审核 → 与 `crm` 客户档案绑定（一对多联系人）。复用 `auth` 模块的 JWT/RBAC，新增 `portal` 角色域，权限码独立命名空间（`portal:*`），与内部账号完全隔离。
- **服务目录与下单**：V1 的"商城购物车"降级为**服务目录页**（试验能力清单：风洞试验类型、数值风洞计算、价格说明）+ **下单向导**（选服务 → 上传数模/填参数 → 提交）。订单即 `contract` 的"意向单"前置状态，审核通过后转正式合同，复用现有合同审批流。
- **进度可视**：客户门户只读视图——订单状态、排队信息、试验进度（由任务状态回流）、交付物下载（报告/数据附件，MinIO 签名 URL 限时下载）。
- **外来试验人员**：挂 `crm` 联系人扩展表 `external_personnel`：登记（身份信息+协议文件）→ 客户管理员审核 → 同步数字安保系统（集成层推送，门禁授权）→ 订单完成/信誉降级自动取消授权（领域事件 `ContractFinished` 触发）。
- **通知**：企业微信为主（已有集成），客户无企微时短信兜底（阿里云短信，配置化）。

### 3.3 试验实施（task + lab）

现有 `task` 模块（任务列表/甘特/详情页签/报告关联）扩展：

- **任务来源**：① 合同审批通过自动创建（现有）；② TMS 同步（集成层适配器，Webhook 写入）；③ 手工新建。
- **试验排程**：新增 `lab_schedule`：按设备/工位占用自动预排 + 甘特图手工拖拽调整（复用现有任务甘特组件扩展资源维度）；客户信誉度影响优先级排序。V1 提到"大数据平台给排程建议"——一期先规则引擎（设备空闲+优先级+工期），算法建议后移。
- **样车出入库**：PAD H5 页（响应式复用现有前端体系），扫二维码（样车编码绑定，编号规则模块发码）→ 点检表单 → 入库；非负责人点检推送负责人审核（走现有审批引擎）；试验完成推送复原点检单。
- **试验整备与工时**：PDA 扫 NFC/二维码切换工位与任务；整备附件清单按任务类型从字典配置；拆装件强制拍照上传（MinIO）；工时 = 扫码上岗/离岗时间差，按任务归集，供结算取用。
- **试验数据**：自动采集（IoT 层，见 §5）+ 人工录入导入（Excel 模板）；原始文件进 MinIO，结构化结果入 MySQL，按任务绑定；一键推送 TDC / 触发报告生成（report 模块）。

### 3.4 数值风洞（sim）

- `sim_task`：对内（任务工况页一键发起）/对外（客户门户下单）统一入口；参数（风速、边界层配置）表单化；数模上传走 MinIO 分片。
- 生命周期：提交 → 调仿真管理平台 API → 排队/进度回写（轮询 + Webhook 双通道）→ 完成 → 后处理数据（图片 + JSON）拉回展示，报告（PPT/PDF）归档 MinIO 并可挂到任务交付物。
- `sim_template`：数值风洞模型模板缓存表，从仿真平台拉取，支持编辑后回推。
- 取消规则：未启动/计算中可取消（调对方接口）；客户取消订单联动取消（领域事件）。

### 3.5 设备管理（device）

| 子功能 | 实现要点 |
|---|---|
| 台账与工位 | `device`、`workstation` 表；工位忙闲由 NFC 上岗扫描驱动，二维平面图（SVG 标注，不上三维）展示状态颜色 |
| 预警管理 | 规则引擎（阈值/表达式，字典化配置）+ 分级分类推送（企微通知，推送对象按角色配置）；记录查询导出；预警数据同时进 TDengine 供后续预测性维护训练 |
| 能耗管理 | IoT 层 7×24 采集进 TDengine；采集点/频率/存储策略可配置；按任务时间区间截取计算（结算取数的关键）；按天汇总推送设备在线系统 |
| 点检管理 | 二维地图标记点位（EAM 同步设备点位）；NFC 扫码激活填报页（PAD H5）；异常按级别同步 EAM + 通知设备负责人 |
| 物料管理 | 备件/耗材表（型号/厂商/报价/到货周期）；二维码出入库（编号规则发码）；出库类型（项目/维保/接待）关联任务；低库存阈值预警；结算阶段可补录耗材并回写库存 |
| 设备数据 | 采样变量配置表（变量/周期/存储时长）驱动 IoT 采集服务；时域/频域分析用 ECharts + 后端聚合 API；故障库（故障代码/指导文件/照片视频，全文检索） |
| 环境设备 | 照明/空调/温湿度/有害气体：经 IoT 网关对接控制系统，只读状态先行，远程控制二期（安全审慎） |

### 3.6 虚拟结算（finance 扩展）

现有财务链路（核算→结算单 K 号→开票申请→到账登记 DZ 号）**不变**，扩展的是结算单的数据来源：

- 任务结束（`TaskFinished` 事件）自动触发"结算数据归集"：按任务绑定汇总 ① 能耗（TDengine 按工况起止时间截取）② 工时（lab 扫码记录）③ 耗材（device 物料出库+结算补录）→ 生成结算草稿明细 → 结算人员确认 → 结算单审批（现有流程）。
- 结算模板：结算项与计算规则字典化（`dict` 模块），V1 的"对接 DMDS 结算模板"作为适配器预留。
- 统计视图：按任务/试验类型/人员/周期的能耗、工时、耗材统计与导出（ECharts + 导出中心）。

### 3.7 安全管理（safety）

- **智能监控**：不自建视频 AI——对接现有视频监控系统的告警 API（冒烟/起火/漏水/电子围栏越界），告警入 `safety_alert` 表并分级推送；监控画面以播放器组件嵌入（RTSP 转 HLS/FLV）。
- **消防管理**：消防告警对接消防系统接口；月度点检单定时推送（APScheduler + 企微），NFC 扫码填报。
- **安全巡检**：每日巡检/离场确认表单（多表单：人/设备/环境，设备状态由系统预判定=最近采集值是否超阈），二维图纸 NFC 点位配置，逾期未检升级提醒。

### 3.8 数字孪生（twin）

- 前端 Three.js 场景：实验室三维环境（模型离线建模导入 glTF），设备状态/参数实时叠加（WebSocket 推送，IoT 层订阅转发）。
- 大屏与 VIP 室 TV：只读视图（当前任务、样车工位、风机转速/光照/转鼓功率实时数据、试验结果），路由独立、免登录令牌访问（大屏专用只读 token）。
- 反向控制（照明/空调）二期开放，且仅内网 + 二次确认 + 审计。
- 数模轻量化：数模文件后台转 glTF（异步任务），供孪生场景展示。

### 3.9 接口管理（admin 集成域扩展）

技术设计文档 §8.7 已设计"集成与开放域"（连接配置/凭证加密/连通性测试/推送记录重放），本期补齐管理界面，19 项外部系统全部登记为"连接器"：协议（REST/MQTT/数据库直连/文件）、地址、凭证（加密存储）、字段映射、启停状态、最近推送日志。

## 5. IoT 采集层设计

```
设备/传感器 ── Modbus/OPC UA/串口 ──► 边缘网关(DTU/工控机)
                                          │  MQTT（TLS，内网）
                                          ▼
                              采集服务 collector（Python asyncio）
                                ├─ 写 TDengine（批量入库）
                                ├─ 触发预警规则评估（Redis 订阅）
                                └─ WebSocket 网关 → 大屏/孪生实时推送
```

- **协议适配**：采集服务按 `device_point` 配置动态生成采集任务；Modbus TCP/RTU（pymodbus）、OPC UA（asyncua）、MQTT 上行（DTU 场景）三类适配器起步，新增协议按插件注册。
- **可靠性**：断网本地缓存（网关侧 SQLite 暂存，恢复后补传）；采集服务无主多实例 + Redis 锁防重复采集。
- **实时推送**：WebSocket 网关复用 FastAPI（`/ws`），按主题订阅（工位/设备/任务），大屏与孪生前端消费。
- **NFC/二维码**：PAD/PDA 端用 H5（企微浏览器或系统浏览器）+ 设备 NFC 读头/扫码枪，不开发原生 App（V1 提钉钉集成，企微同理可挂 H5 应用，优先级低于 Web）。

## 7. 安全与等保三级落地

在现有能力（JWT、bcrypt、RBAC 权限码、审计日志、踢人/多端策略）之上补齐：

| 等保要求 | 落地措施 |
|---|---|
| 身份鉴别（多因素） | 登录加图形验证码/企微扫码二次确认（高危操作）；密码策略（长度/复杂度/定期更换/错误锁定）已有雏形需补全 |
| 传输加密 | 全站 HTTPS（nginx 终止）+ 内网服务间 mTLS（二期）；MQTT 走 TLS |
| 数据加密存储 | 身份证/税号/银行账号字段级 AES 加密（密钥走环境变量+KMS 预留）；凭证表加密已有设计 |
| 数据分级 | 客户数据/财务数据/试验原始数据三级，导出与下载全部审计 |
| 备份恢复 | MySQL 每日全量+binlog；TDengine 快照；MinIO 版本控制+异地同步（二期）；恢复演练每季度 |
| 日志审计 | 现有审计日志扩展采集 IoT/集成层事件；日志留存 ≥6 个月 |
| 边界防护 | 客户门户与内网管理端分离部署（独立域名+WAF），门户账号权限码隔离 |
| 大文件上传安全 | 分片校验+类型白名单+病毒扫描接口预留 |

## 9. 实施路线图

> **总体策略（2026-10 拍板）：当前系统基座（bizSys）优先完善，风洞数字化的其余模块全部作为下一步开发计划。** 风洞各阶段（P1~P4）以 P0 基座验收为启动门槛——客户、合同、任务、报告、财务、审批这些主干不扎实，上层的排程、结算归集、客户门户都是空中楼阁。

### P0 基座完善（当前最高优先级）

bizSys MVP 主干已通（CRM/合同/任务/财务/审批/企微绑定），以下收尾项完成后基座才算可支撑风洞扩展：

| # | 事项 | 验收口径 | 对应文档 |
|---|---|---|---|
| 1 | **报告全流程闭环**：报告起草 → 审批 → LibreOffice 转 PDF → 电子签章 → 归档 → 挂任务交付物 | 一份报告从任务发起到盖章归档全程线上完成 | 技术设计文档 §10.4、会议记录"出报告敲章" |
| 2 | **企业微信深化**：SSO 扫码免登、组织架构同步、消息/待办推送 | 企微扫码直接登录；审批待办实时推送到企微 | 技术设计文档 §9 |
| 3 | **WTCS 适配器接口冻结 + Mock 服务**：任务推送/进度回写接口定稿，Mock 先行 | 接口契约评审通过，Mock 可跑通任务推送→回写闭环 | §10.4、§11 |
| 4 | **表单体验补齐**：能做选择的不让录入（全站下拉/字典化复查）、输入自动完成与智能补全 | 高频表单（合同/任务/客户/财务）零自由文本硬伤字段 | 会议记录 UX 要求 |
| 5 | **通知中心**：站内待办/消息聚合页，审批/财务/任务状态变更统一触达 | 工作台待办与通知中心数据一致 | workbench 已有雏形 |
| 6 | **数据权限**：行级/部门级数据可见性（销售只看自己的客户合同） | 非管理员角色越权访问测试全阻 | §13 安全设计 |
| 7 | **异步导出中心**：大报表/大清单导出走异步任务 + 进度提示 | 10 万行级导出不阻塞页面 | §8 指标 |
| 8 | **备份与运维基线**：MySQL 每日备份脚本、健康检查端点、审计日志留存策略 | 备份恢复演练一次通过 | §7 等保要求 |
| 9 | **AI 底座（可选插档）**：LLM 网关 + 系统设置 AI 卡片 | 见 `docs/ai-todolist.md`，不与上述项争资源 | ai-todolist §0 |
| 10 | **流程驱动改造**：引擎合并 TPCworkflow 语义（可视化设计器/条件分支/会签/抄送/表单引擎）+ 业务全量"提交即流程" + OA 配置化上线 | 合同/任务/报告/财务提交即发起流程；OA 单据零代码可配 | `docs/流程驱动架构与TPCworkflow整合方案.md` F1~F4 |

P0 完成标志：上表 1~8 全部验收，系统在无供应商方案任何新模块的情况下，作为公司 ERP 独立稳定运行。

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 设备协议繁杂（17 台设备、协议未知） | 高 | P1 只做 2~3 台试点验证采集链路；协议调研前置为 P1 第一周任务 |
